Good practices

For anything bigger than a little project like this, it’s worth getting some structure into your code. It’ll help to avoid common pitfalls and save you time and resources.

Some questions to ask yourself:

  1. How should we arrange the code inside the project so it’s easiest to work with?
  2. Once it’s written, how do we know it will work?

Common conventions

When your AI assistant is working for you, it builds itself a context - which contains all the information it has learned (your prompts, its responses, all the code files it has read, the things it has done, etc.) As your conversation grows, so does the context. The larger it is, the more work (and tokens) it needs to work through to get anything done.

You’re either paying for tokens, or you have a free tier budget. Either way, let’s take a look at some practices that will help you keep your context small…

NB. opencode can make its context smaller by compacting it. This is often done by figure out what it can safely lose, and still be useful. It will very likely replace what it dropped from the context with a shorter summary, so that it doesn’t forget everything entirely. This is helpful, but there’s plenty you can do to achieve more.

Software development is a discipline - and has developed some common ways of working that make it easier to work collaboratively.

  • Documentation: By documenting the project, you and your assistant will have access to a useful summary of the code it has created.

  • Conventions: By following common patterns and conventions, you and your assistant can share a common language. You won’t need to clarify so many things, and it’ll have a much better clue about where to find the parts of the project it needs, and how to use them.

Documentation often lives in a folder called docs/ in the repository. Keeping it close to the code by keeping it in the repository is good. It’s quick and easy for a developer to find, and your coding assistant can also use it.

Some conventions are built into frameworks, which act like bumpers - forcing development into a structure. This often means that the code you write will be reusable and easy to debug or fix.

Streamlit is one such framework, and it helps to build complex projects with user interfaces that are much easier to maintain than other ways of acheving the same thing.

Other conventions are code quality constraints. These are often rules to help developers write code that’s easy to follow, easy to change, and easy to reuse. There are some common guidlines known to developers to help with this…

DRY (Don’t Repeat Yourself)

If you find that you’ve written the same function more than once, it’s a candidate for deduplication.

In the ideal case, you’d only write it once, and call it from everywhere it’s needed.

This is important because most of our assumptions, when we write code, will be challenged. It’s very likely you’ll need to change those functions. For every duplicate, that’s an extra step - and another point in the code base you could forget about.

Some developers are more relaxed about this, and there’s a case to say that if something only appears twice, it might be more effort to combine those instances than it’s worth.

This is very much a judgement call - and something you’ll want to tell your coding assistant about upfront as a part of the coding standards you lay down.

I instinctively err on the side of deduplication. As code bases get bigger and more complex, you may not be able to remember where all the instances are, and it becomes harder to maintain. Better to nip it in the bud.

Testing

When you alter code in a software project, it’s very likely you’ll also alter something you didn’t mean to, too. That’s the nature of complex tasks like coding. After a few surprises, you’ll come to the conclusion that there ought to be a way to catch mistakes.

  • Automated tests: There are testing frameworks for every language and framework.

This is essential for every project, and it’ll get a whole post. Without it, you’ll be reduced to manually testing every feature every time you make a change.
